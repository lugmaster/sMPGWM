# UI and player input

`GamePlayManager` connects the scene's UI, input controller, and player action controller. Singleton dependencies use `InputController.Instance` and `PlayerMock.Instance`; ordinary scene nodes still use `GetNode`. Its session state is either `Active` or `Inactive`; opening a window does not change session state or pause the world.

## Responsibilities

| Component | Responsibility |
| --- | --- |
| `UiCanvas` | Exposes four public menu operations and forwards UI requests; receives data through internal gameplay integration methods. |
| `UiWindowManager` | Creates, closes, and focuses windows in centered, wrapping rows; handles menu shortcuts and scrolls focused windows into view. |
| `UiWindowRegistry` | Tracks open window identities, focus order, and whether any window blocks player controls. Contains no Godot dependencies. |
| `PlayerInputPolicy` | Derives `CanControlPlayer` from an active session, no blocking windows, and no pending message acknowledgement. Contains no Godot dependencies. |
| `InputController` | Gates continuous movement/combat input, clears outputs when blocked or unfocused, and suppresses mouse attacks over UI. |
| `PlayerActionController` | Accepts hotbar activation requests and checks policy and current input availability before invoking gameplay. |

## Window behavior

`MainGame` keeps the world in a window-filling `SubViewport` and renders UI through the single `UiCanvas` CanvasLayer in the root viewport. The project's `canvas_items` stretch mode keeps UI rendering at the window resolution. Inside `UiCanvas/Root`, scene-tree order defines the UI draw order: `Hudlayer` (including the hotbar), `MenuLayer`, then `ItemPointerOverlay`. These branches are Controls; individual HUD widgets and pointer visuals do not create CanvasLayers or override ordering with Z indices. Pointer visuals and their children ignore mouse input.

`MenuLayer/UiContainer` defines the maximum visible area for overlay menus using proportional anchors: left 15%, top 11%, right 85%, bottom 88% of the UI root. This centers the menu area horizontally with equal 15% side margins and leaves space for HUD elements and follows the marked reference layout when the window resizes. The supported UI baseline is 1920x1080; smaller UI windows are outside the current support target. The world SubViewport follows the full-rect viewport container through `stretch = true`; both the container and `MainGame` use full-rect anchors. It clips its descendants; the menu host and window scroll surface fill this rectangle. Windows wrap into another row when they cannot fit beside the previous window. Tall content scrolls vertically within this area; horizontal scrolling is disabled. This layout boundary keeps inventory-to-hotbar click and native drag editing available without elevating the hotbar above menus. Adjust the container's anchors to change the allowed menu area.

- Inventory, Map, and Messages can coexist. Main menu is exclusive: opening it closes other windows. Activating another menu closes Main Menu and opens the requested menu. The toolbar remains interactive; the full-screen mouse input blocker is reserved for required message acknowledgements. Each menu blocks player controls.
- `UiCanvas.OpenMenu(id)` creates one instance or activates the existing instance and scrolls it into view. Window activation tracks window order independently of GUI keyboard focus; it never selects Close automatically. Activation preserves focus within that window and releases focus belonging to other controls.
- `UiCanvas.CloseMenu(id)` closes that window; `ToggleMenu(id)` opens or closes it. Close buttons close their own window.
- `UiCanvas.CloseAllMenus()` closes every window.
- Clicking a window updates focus without changing its position in the row. Escape toggles Main Menu: it closes all other windows and opens Main Menu on one press, or closes Main Menu if it is already open.
- Mouse clicks use Godot 4.6's native focus behavior: buttons retain hover/pressed feedback without a forced keyboard outline. Tab/arrow navigation and Enter/Space activation retain visible keyboard focus across start menus, overlays, HUD buttons, item cells, and message controls. Search takes focus on click; clicking elsewhere releases it, while wheel scrolling preserves it. Decorative controls never receive focus.
- Escape is handled before focused GUI controls can consume it, including after clicking a hotbar button or while editing search text. Other menu shortcuts use unhandled input so text entry retains shortcut letters.
- Menu shortcuts execute once per press and require release before another toggle. Duplicate non-repeat key events and keyboard auto-repeat are ignored. Releases are tracked before GUI handling; disabling navigation or losing application/window focus clears the guards. No timed cooldown is used.
- Closing the final blocking window restores player controls only if the session is active.
- Entering `Inactive` closes windows and prevents reopening them.
- HUD processing continues while windows are open. Inventory keeps hotbar buttons interactive for editing while activation stays blocked; other blocking windows alone disable them.
- Held movement resumes when controls become available. Held combat actions require release and a fresh press.

Windows use an `HFlowContainer` inside a vertical-only `ScrollContainer` constrained by `UiContainer`. Each row is centered horizontally within the usable area (excluding the vertical scrollbar), with 20-pixel horizontal and vertical gaps. Windows remain in opening order and wrap beneath the previous row when the next window cannot fit. A shorter window is centered vertically alongside its neighbors. The whole flow is centered vertically when it fits. Opening, closing, content size changes, and viewport resizing automatically update placement. The window manager refreshes scroll extents when the content minimum size changes and scrolls focused windows into view. Empty content is hidden so the scroll container does not intercept HUD or world input.

Placement changes are immediate. Window dragging, resizing, and modal dialogs are deferred. Items support click pickup/placement and native Godot drag-and-drop. The inventory uses eight columns.

## Inventory view binding

`IconSize` is the shared sizing vocabulary: `Small` uses 24-pixel artwork; inventory and equipment select `Medium` (40-pixel artwork); hotbar definitions select `Large` (56-pixel artwork). `ClickableIcon` adds theme padding to that size and fits textures proportionally into the content area. Centered sizing flags prevent container stretching. Texture dimensions and empty/occupied state do not determine button dimensions. With the current theme, hotbar buttons are 64×64 and inventory/equipment buttons are 48×48.

`GamePlayManager` binds its inventory, equipment, and single owned transfer service directly through `UiCanvas.BindInventory` during initialization, exposing `IInventoryView`, `IEquipmentView`, and `IItemTransfers` to the UI. The view contracts expose immutable snapshots and committed change notifications; equipment also exposes its slot definitions. UI code receives no concrete inventory/equipment owners or lifetime operations. The transfer contract exposes only validation and commit. Gameplay opens and revokes edit sessions in response to inventory-window and application-focus availability, then passes the session token to the UI; the UI cannot issue sessions through its contracts. Gameplay retains inventory additions and owner disposal, while transfer preparation and installation remain internal to the domain implementation. The window manager announces individual window openings before adding them to the tree and identifies closed windows. Inventory views accept data before `_Ready`, replace editor preview cells, subscribe to committed snapshots, and detach on closure and teardown. Opening a view renders current state immediately; reopening preserves game-owned capacity and UI-owned toolbar choices.

`InventoryProjection` combines catalog-derived category tabs with trimmed, case-insensitive item-name search and Name ascending/descending sorting. The Weapons category groups Light, Medium, and Heavy in that order and supports filtering by size. Name ties retain definition-ID then entity-ID order in both directions. Matching occupied results pack together, followed by genuine empty addresses; hidden items never become drop destinations. A no-match message can coexist with genuine empties, while a full bag with no matches exposes no cells. These operations preserve storage and revisions. Each cell retains an immutable binding with its actual address/slot key, entity expectation, and revision. `ItemGrid` reuses controls during refresh and appends cells on growth. Equipment labels come from domain slot definitions through the existing labeled-icon scene/provider. Generic icons accept opaque bindings without querying gameplay services.

The Ship equipment tab includes the Weapon Fixture. The Weapons tab uses a VBox with a centered `icon_with_label` counter above the existing `item_grid.tscn`. The counter shows free/max weapon capacity from the equipment snapshot. Nine weapon cells are retained in a grid with three columns, but only equipped weapons and one empty destination are visible while capacity remains. With no fixture, all weapon cells are hidden; a newly equipped fixture initially reveals one empty cell. The grid's height follows its visible rows, up to three rows. Each weapon uses one UI cell; Light, Medium, and Heavy consume one, two, and three capacity units respectively. Hidden cells retain their stable equipment slot bindings. Transfer eligibility and fixture-removal consequences remain domain rules. UI rendering never moves or unequips items.

Inventory-specific lifecycle and application focus authorize/revoke domain edit sessions independently of other blocking windows. Map alone does not authorize inventory edits. The public canvas boundary remains its four menu operations. Shared item presentation adds resource-loaded textures, neutral missing-icon placeholders, tooltips, and bottom-right quantities through generic `ClickableIcon.SetDisplay` input. Stackable items show quantities including one; nonstackable and empty cells have no badge. Large counts truncate to compact labels through the full `long` range, while tooltips retain exact quantities and configured stack-limit information. The delayed Godot popup uses an input-ignoring themed label and is dismissed on rebinding, focus loss, or closure; `DismissTooltip` also closes tooltips when placement starts. Tooltip data remains available with activation disabled.

`ItemInteractionController` owns one pending source shared by inventory, equipment, and hotbar views, with explicit idle, click-placement, and native-drag modes. It captures location/entity expectations, revisions, edit session, and mapping version; the transfer coordinator owns placement rules. `InventoryMenu` captures the displayed target on press and submits on release, with a pointer-ignoring preview, source highlight, and validated hover feedback. Successful click placement ends carrying; incompatible/full-stack click targets retain it. Source/outside/right clicks, toolbar changes, snapshot refresh, focus loss, closure, and session revocation cancel pending interactions. Placement and cancellation consume pointer events; toolbar clicks still perform their normal operation. Escape replaces inventory with Main Menu through the window manager and cancels carrying. These internal hooks preserve the four public canvas operations.

`ItemCellBinding` supplies the actual storage location or hotbar position, entity expectation, and revision for every interactive cell. Cells forward virtual Godot GUI/drag callbacks and hover/tree notifications through plain C# events and delegates registered once at creation; refreshed data does not rebuild those handlers. The menu retains source and hover controls directly and validates feedback on target transitions. Per-frame work only positions the pointer preview and feedback, which are authored in the inventory scene. Hotbar control references are cached. All handlers detach on cell removal or view teardown. Cell dispatch does not use Godot signals, Callable wrappers, or SetDragForwarding.

`UiSystem/Items` contains shared visual formatting and icon resolution for inventory, equipment, and the hotbar. Resolution uses the item asset first, then its category asset/key, then a shared placeholder. Native category tabs carry optional resolved icons and stable category-ID metadata. Iconless categories remain text-only. `ResourceLoader` supplies texture caching; views do not maintain parallel texture dictionaries. YAML loading validates icon keys and references from the shared equipment slot definitions before gameplay construction and returns structured errors with source paths.

Transfer hover checks evaluate the two affected locations without creating entities, slot arrays, or global identity sets. Commit revalidates the request, prepares immutable snapshots, verifies global identity uniqueness, installs both owners, then publishes notifications. `InventoryChangePlan` remains internal because its owner/before-snapshot checks protect installation; each `ItemEntity` references its immutable `ItemDefinition` for icons, tooltip content, and stack limits. Definition and category IDs are strings; entity IDs remain typed. `ItemRegistry` loads YAML once per application lifetime and shares final definitions across inventory, equipment, hotbar, and UI. The redundant category-tab model and separate inventory, equipment, and hotbar cell binding records have been removed.

`GamePlayManager` owns and disposes `ItemHotbarController`, which owns its internal ten-position `ItemHotbarState`. Gameplay hotbar types live in `Scripts/ItemSystem/Hotbar`; the UI control lives in `UiSystem/HudSystem/Hotbar`. UI consumers receive only the controller: it exposes editing, resolution, activation, and a combined change notification for state, inventory, and equipment. Inventory and equipment subscriptions remain active until disposal so unequipped weapon bindings are cleared even without UI listeners. Assignment uses `HotbarAssignmentRequest` with separate `ValidateAssignment` and `Assign` methods; preview and commit share source validation. The state owns immutable binding snapshots, edit sessions, revisions, and publication protection. `HotbarControl` renders slots and forwards clicks. Consumable links sum matching inventory stacks with `long` quantities and retain their definition at zero. Weapon links resolve stable equipment-slot keys on each committed refresh and are cleared when their weapon cell becomes empty, including automatic returns after fixture removal or a capacity reduction. Mock action bindings live in gameplay integration and preserve original action identity through rearrangement. Item activation produces a typed integration request/log; it does not consume items or execute effects. PlayerActionController remains the final activation gate.

While inventory is open in an active, focused session, the menu's click/native drag adapters can assign eligible sources, move/swap existing hotbar entries, or right-click to cancel and clear one position. Assignments replace the destination without changing ownership. Inventory weapons and unsupported categories are rejected. Links cannot transfer into inventory/equipment; outside drops cancel. Hotbar edits use the same short-lived edit session plus hotbar/source revisions. The menu layout leaves the hotbar strip unobstructed within the shared UI canvas. Closing inventory revokes editing immediately, including when Map remains open; activation permissions are independent. Generic ClickableIcon still contains no item services.

Slot-specific delegates registered through `SetDragForwarding` adapt native Godot drag callbacks without adding inventory dependencies to `ClickableIcon`. Godot controls the drag threshold and preview; payloads contain a single-use opaque token scoped to the controller's edit session. Hover validation is read-only, and drops revalidate through the same transfer coordinator as clicks. Every native drag end clears carrying, including invalid, full-stack, and outside drops. Source state remains authoritative until a successful commit. View/session changes cancel the native drag and invalidate its token immediately. Native release does not also trigger click pickup, and wheel scrolling stays available through the existing inventory scroll container.

Normal startup uses PlayerMock examples. `PopulateMockInventory` on `GamePlayManager` defaults to true and can be disabled for an empty bag. PlayerMock uses category icons and seeds 40 occupied inventory cells: duplicate equipment, including fixtures and all three weapon sizes, plus full and partial consumable/resource stacks. The ten hotbar positions start empty; no legacy mock artwork or actions are seeded. Toolbar choices survive transfers and window reopen. Toolbar changes cancel pending placement before refreshing the mapping. Search accepts Inventory/Map shortcut letters as text; Escape still opens Main Menu while search has focus and input releases still clear navigation guards. Filtering refreshes on input or committed snapshots, with scroll preservation/clamping supplied by the existing Godot scroll container.

`UiCanvas` owns a reusable `ItemPointerOverlay` Control as the last child of its shared UI root, drawing above menus and the hotbar within the same canvas. The overlay owns the carried-item icon, placement label, cursor tracking, and native drag preview construction using Godot's `SetDragPreview`. `InventoryMenu` supplies the icon and contextual text after validating the hovered target, and clears the overlay when interaction ends. Closing or reopening inventory reuses the overlay without retaining the previous pickup. Placement rules and slot highlighting remain in the inventory interaction code.

## Messages and HUD toolbar

The upper-right toolbar reads left to right as Messages (including the unread badge), separator, Inventory, Map, Main Menu. All controls use medium icons and named tooltips with configured shortcuts. `MessageMenu` is intentionally unbound in Input Map. The HUD forwards activation through `UiCanvas` to the same internal `UiWindowManager.Activate` operation used by keyboard dispatch. Keyboard repeat/release and text-entry guards stay at the keyboard boundary. Main Menu activation replaces all existing windows with Main Menu immediately; activating it again closes it. Other toolbar buttons and menu shortcuts replace Main Menu with the requested window. Main Menu blocks gameplay and hotbar activation while leaving toolbar navigation available. Empty HUD anchor space ignores mouse input.

`MessageController` owns messages, read flags, and outstanding acknowledgements for each gameplay manager lifetime and is the boundary to the message UI. Register a `MessageSender`, then call `GamePlayManager.Instance.MessageController.Receive(id, senderId, subject, body, MessageType.NonBlocking)` (or `Blocking`). Nonblocking messages default to no outstanding acknowledgement. Immutable snapshots provide sorted messages and unread totals. Duplicate IDs are no-ops; publication rejects nested writes and isolates observer errors.

The controller connects presentation and the player-input policy. Reading does not acknowledge a message. Pending acknowledgements are derived from message state in arrival order. Inactive gameplay retains history and pending confirmations; activation presents the earliest pending confirmation. Disposal detaches the UI and releases the input gate.

Startup receives exactly one nonblocking System message: `Welcome` / `Welcome, this is test message`. It turns the notification yellow with badge `1` without opening a window. There is no persistence or automatic reseeding on menu open. Each explicit Messages action selects and reveals the first unread in display order, displays its content, and marks only that message read. Without unread messages it retains a valid selection, or picks the newest message. Rows can also be selected individually. Nonblocking arrivals update counts and rows without changing selection, folding, detail scrolling, or gameplay. Zero unread keeps the notification clickable, grey, and without a badge; larger badges use shared compact quantity formatting with exact totals in the tooltip.

`UiCanvas` subscribes to the store for the HUD independently of menu lifetime. It binds recreated windows before tree entry and owns `MessageViewState` (stable selection ID, collapsed sender IDs, and pane scroll positions). Windows subscribe before rendering and detach on close/rebind. Sender groups and message rows are reused by stable ID within the append-only store, preserving keyboard focus through arrivals, selection, and read updates. Binding changes clear those controls. One coalesced deferred update restores scrolling, reveals the requested selection, and marks it read after layout; a binding version discards callbacks from previous bindings. A new selection resets body scrolling; unrelated refreshes preserve it. Sender headers and rows are siblings. Long subjects use ellipsis/full-text tooltips; bodies wrap in an independently bounded vertical scroll pane. Empty or unavailable bindings clear both panes.

`MessageController` tracks blocking arrivals independently of read flags. The pending gate in `PlayerInputPolicy` is set before ordinary menus close. Blocking arrival cancels inventory carrying/native drag, closes every menu (including Main Menu), and displays the arrival with a full HUD/world input barrier. Subsequent blockers queue by arrival sequence; nonblocking arrivals cannot steal selection. Browsing and the ordinary close control are disabled. Manager-level guards reject Escape, shortcuts, toolbar actions, and public canvas close/toggle/replacement attempts. Only an actual pointer click on the footer OK acknowledges one message; keyboard button activation cannot acknowledge. Each OK advances the queue, and the final OK closes Messages without restoring interrupted menus. Controls resume only when session/window policy also allows them. The session stays active, world physics keeps running, and the tree never pauses. Replacing or unbinding the message store during a required acknowledgement throws `InvalidOperationException`; rebinding the same store is a no-op that preserves the requirement. `EndMessageSession` is the separate internal teardown path that releases the presentation lock and detaches the store; the controller releases its input gate.

The opt-in `MessageSmokeFixture` supplies Station Command, Trading Guild, Security Office, same-name sender, long-text, empty-binding, large-count, and blocking cases. Normal startup uses only the welcome message. `message_menu_smoke.gd` exercises real pointer/keyboard events at 1920x1080 and 2560x1440 over the unchanged 1280x720 world viewport, including keyboard focus through arrivals and read transitions, row reuse and selection styling with over 1,000 messages, rapid rebinding with queued callbacks, rejection of binding changes during acknowledgement, and teardown with a pending requirement. For rendered evidence:

```powershell
& $godotExecutable --path sMPGWM.Game --script ../sMPGWM.Tests/UiSystem/message_menu_smoke.gd -- --capture-visuals
```

Captures go to `artifacts/messages-*.png`. Keep the OS pointer idle during a rendered run. Headless mode runs the same assertions without screenshots. See the completion record in `docs/plans/message-menu-and-toolbar.md` for commands and outcomes.

## Adding features

The public window boundary is `UiCanvas.OpenMenu`, `CloseMenu`, `ToggleMenu`, and `CloseAllMenus`. Window manager operations, HUD configuration, and gameplay integration members are internal; event-forwarding helpers are private. Godot lifecycle overrides remain public. The registry and scene provider are internal, with `InternalsVisibleTo` granting NUnit access to the registry's state logic.

Window identities and Godot Input Map actions share exactly the same names: `UiWindowId.InventoryMenu`, `MapMenu`, `MainMenu`, and `MessageMenu`. The manager enumerates the enum to derive cached `StringName` values and tracks held actions using enum values. There is no separate action-name list or string switch.

To add a menu, create an inherited `game_overlay_menu.tscn` scene and a script extending `GameOverlayMenu`. Add its enum value (for example, `SkillTreeMenu`), its scene creation method and factory case, and an identically named Input Map action with the desired hotkey. Inventory and Map actions toggle the matching window; Messages opens/focuses and selects the first unread message; `MainMenu` toggles the exclusive main menu, including when Escape is pressed while another window is open. When renaming an enum value, update the Input Map entry too; the configuration test checks their alignment. Keep window navigation inside the UI. The registry supports nonblocking windows, although all current factory cases use blocking windows.

For example, gameplay code holding a canvas reference opens inventory with `canvas.OpenMenu(UiWindowId.InventoryMenu)`.

Route feature requests to the owning gameplay controller: inventory views request item moves, trade views request offer changes, and passive tree views request allocations. Those systems validate and change authoritative state; the views refresh from the resulting state. Keep selections, hover states, and drag previews in the views.

Hotbar buttons use `PlayerActionController.RequestHotbarActivation`. Future keyboard hotbar bindings should call the same method. Gameplay resolves each display position to its original mock action or its currently available item link. Item effects and networking remain deferred.

## Verification

From the repository root:

```powershell
dotnet build sMPGWM.sln
dotnet test sMPGWM.Tests/sMPGWM.Tests.csproj
& $godotExecutable --headless --path sMPGWM.Game --script ../sMPGWM.Tests/UiSystem/ui_architecture_smoke.gd
& $godotExecutable --headless --path sMPGWM.Game --script ../sMPGWM.Tests/UiSystem/icon_sizing_smoke.gd
& $godotExecutable --headless --path sMPGWM.Game --script ../sMPGWM.Tests/UiSystem/inventory_smoke.gd
```

Set `$godotExecutable` to the Godot .NET console executable. The smoke script loads the actual game scene twice and checks row placement, scrolling, window navigation, focus, input blocking, hotbar interaction, and teardown. It runs the project's normal autoloads, including Steam initialization.

The sizing smoke checks hotbar, inventory, and equipment at both viewport sizes with 16-, 64-, and 256-pixel textures, a rectangular texture, and empty slots. It verifies that texture changes preserve the configured slot dimensions, including the hotbar while inventory is open.

The inventory smoke checks default PlayerMock startup data and empty hotbar slots, then disables demo seeding for empty-inventory checks. It covers cell rendering, view-choice retention, vertical bag scrolling, multi-window wrapping, focus visibility, recentering, and teardown at 1920x1080 and 2560x1440, with the world viewport remaining 1280x720. Fixture-based rebinding and transfer interaction checks have been removed; domain unit tests remain. The architecture smoke verifies adjacent windows at a wide viewport, then enlarges map content and narrows the viewport to verify wrapping, vertical scrolling, and focus visibility. It also verifies exclusive main-menu navigation and Escape after clicking the hotbar.

For rendered visual evidence, run `& $godotExecutable --path sMPGWM.Game --script ../sMPGWM.Tests/UiSystem/inventory_smoke.gd -- --capture-visuals`. This saves window-overflow screenshots for each resolution to `artifacts/inventory-inv10-*.png`. It requires a desktop and focuses the test window. The current demo starts with PlayerMock items and an empty hotbar.
